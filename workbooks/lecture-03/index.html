Review and Algorithms

The problem-solving framework

In Lecture 2 we used six activities: understand, decompose, recognise patterns, design and evaluate, implement, and reflect. These activities help us think about a task. We can revisit them when a check reveals something we missed.

For the pizza order, a three-person example showed that the first sharing method needed another agreement. We will now express the revised method more precisely, draw its paths, and see a supplied program carry it out.

The pizza agreement

The shop charges a flat CA$10 delivery fee. Tax is 15% of food plus delivery. Round tax to the nearest cent; an exact half-cent rounds upward. The group agrees on a dollar tip, which is not taxed. Everyone pays an equal amount, in whole cents. There must be a whole number of people of at least one.

If equal payments would need fractions of a cent, the group permits the smallest increase in the tip that makes equal whole-cent payments possible. Report the changed tip and total as well as each person's payment. There are no other charges in this example. Use nonnegative food prices and tip amounts in whole cents.

The order from Lecture 2:

Food pricesCA$25 + CA$25 + CA$20 = CA$70
Food plus deliveryCA$70 + CA$10 = CA$80
Tax80 × 0.15 = CA$12
Agreed tipCA$8
Initial totalCA$80 + CA$12 + CA$8 = CA$100

An algorithm

An algorithm is an ordered method with clear actions that can be carried out and that finishes. A precise instruction removes a choice that the person following the method would otherwise have to guess. “Split fairly” is not precise enough. The whole-cent rule above tells us what to do.

The algorithm from Lecture 2 is:

  1. Obtain pizza prices, the agreed tip, and a whole number of people of at least 1.
  2. Add the prices, then add CA$10 for delivery.
  3. Multiply by 0.15; round tax to the nearest cent, half-cent upward.
  4. Add this tax and the agreed tip to food plus delivery.
  5. Convert the total to cents.
  6. Until it divides into whole cents per person, add one cent to the tip and total.
  7. Divide the final total in cents by the number of people.
  8. Report the final tip, total, and payment in dollars and cents.

The algorithm is the method. Plain English, pseudocode and a flowchart can describe that same method. A Python program can implement it. You do not have to produce all these representations for every problem.

Progress and stopping

For three people, 10000 cents does not divide into equal whole-cent payments. Neither does 10001. But 10002 does: each person pays 3334 cents. Each repetition increases the total by one cent. With a positive whole-number group size, this eventually reaches a total that divides equally. The first such total gives the smallest increase. The method then stops adjusting.

A method can be precise and finish but still give an incorrect result. We must also compare its result with the agreement.

Pseudocode

Pseudocode describes instructions in structured words for people to read. It is not executable Python. We use a few consistent words to make the method easy to follow: READ obtains information, SET calculates or stores a named value, and DISPLAY shows a result. A named value is a label for information used by the method.

For example, these steps obtain prices, add them, and show the food cost:

READ pizza prices
SET food TO the sum of the prices
DISPLAY food

With prices CA$25, CA$25 and CA$20, the food cost is CA$70.

Inputs and decisions

A condition is a statement that is true or false. A decision chooses actions according to a condition. Indentation groups the actions belonging to a choice. ELSE introduces what happens when the condition is false.

Check the group size before calculating a payment:

READ people
IF people is a whole number at least 1
    Continue to the bill calculation
ELSE
    DISPLAY the group-size message
    STOP
END IF

The group-size message is: Enter a whole number of people of at least 1. Three people pass the check. Zero people do not. A value such as 2.5 also fails because it is not a whole number. On failure, show the message and stop; this method does not ask again automatically.

Calculation and repetition

The subtotal is food plus delivery. Calculate tax from this subtotal, round it, and then add the rounded tax and tip. Keep calculations in an order that makes each value available before it is needed.

We use cents for the adjustment: CA$100 becomes 10000 cents and CA$8 becomes 800 cents. “Total needs adjustment” means the total cannot yet divide into whole cents per person. WHILE checks this condition before each repetition. The indented actions both happen before the next check. When the condition is false, continue after END WHILE.

The complete pseudocode:

READ pizza prices, tip, people
IF the group size is invalid
    DISPLAY the group-size message
    STOP
END IF
SET food TO the sum of the prices
SET subtotal TO food + 10 dollars
SET tax TO 15% of subtotal
ROUND tax to cents, half-cent upward
SET total TO subtotal + tax + tip
CONVERT total and tip to cents
WHILE total needs adjustment
    ADD 1 cent to total
    ADD 1 cent to tip
END WHILE
SET payment TO total divided by people
DISPLAY final tip, total and payment
        in dollars and cents

Here the input check states the invalid case first. It is equivalent to the earlier IF/ELSE: an invalid group stops, and a valid group continues. The group-size message and “needs adjustment” have the meanings defined above.

Normal and boundary cases

A normal case uses ordinary valid input. A boundary case checks a limit, such as the smallest valid group of one person. Also check inputs just outside a limit, such as zero people, to see whether the method rejects them.

For every valid case, multiply each payment by the number of people. This must equal the revised total. Also check that subtotal, rounded tax and final tip add to that same total.

Flowcharts

A flowchart draws the steps and the paths between them. Follow arrows to find the next step. A rounded start/end shape marks a beginning or finish. A rectangle contains an action; a slanted input/output shape obtains information or shows a result. A diamond contains a condition with labelled Yes and No exits.

A decision

The group-size condition chooses between continuing and stopping. For three people, follow Yes. For zero, follow No and show the message.

A repeated action

The return arrow brings us back to the condition after both amounts change. The decision uses the same “needs adjustment” condition as the pseudocode.

For three people, the route is Yes, Yes, No. For four, the first answer is No, so the adjustment is skipped. Both representations produce the same amounts.

Using IDLE

IDLE has an editor where the saved script appears and a Shell where interaction and results appear. The script is saved in a file whose name ends in .py, such as pizza.py.

  1. Open the supplied script in IDLE's editor.
  2. Use File → Save As to save your working copy in a known folder.
  3. In the editor, choose Run → Run Module.
  4. In the Shell, respond to each prompt. Enter prices separated by spaces, without currency symbols. Use at least one price. Prices and tip are nonnegative amounts with no fractions of a cent. Enter the group size as a number.
  5. Compare the results with the expected amounts. To use different inputs, run the saved script again.

The editor contains the method. The Shell shows one run of it. Merely opening the file does not run the program.

Comparing Representations and Reflecting

The plain-English algorithm states what to do. Pseudocode groups instructions and makes decisions and repetition explicit. The flowchart shows the same paths with arrows. The script carries out the method and produces results we can check. Changing the representation should preserve the agreed calculation and results.

In the pizza problem, the initial division needed fractions of a cent for three people. Revisiting the agreement gave a new rule: increase the tip by the smallest necessary amount. Tracing and running the revised solution both give tip CA$8.02, total CA$100.02 and three payments of CA$33.34.

Reflection means explaining what changed, why it changed, and what the evidence shows. The useful lesson is to check the real requirements, including units and limits. Use a representation because it helps you think; these are not compulsory stages to repeat for every task.
